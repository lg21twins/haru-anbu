# 실증(파일럿) 계획 v1 — 현실 점검판

> 2026-08-02. `03_제안서_본문_v1.md` §8의 상세본.
> 이 문서의 목적은 "파일럿을 하겠다"는 선언이 아니라 **"지금 상태로는 파일럿을 할 수 없다"는 사실부터 정직하게 적고, 그 간격을 메우는 순서를 정하는 것**이다.

## 0. 먼저 인정할 것 — 지금은 파일럿이 불가능하다

2026-08-02 저장소 점검 결과:

| 점검 항목 | 실제 상태 |
|---|---|
| 4역할 화면 | **있음** — 고유 화면 39개(언어 변형 포함 67개 파일), 클릭 가능한 고충실도 프로토타입 |
| 서버·데이터베이스 | **없음** |
| 로그인·인증·권한 | **없음** (화면만 존재) |
| 앱 → 서버 통신 | **없음** — 앱 HTML에서 `fetch`·API 호출 **0건**. 데이터는 전부 화면에 하드코딩 |
| 푸시 알림 | **없음** |
| AI 리포트 생성 | **없음** (문구는 사람이 작성한 예시) |
| 법인격·계약 주체 | **없음** |
| 앱스토어 배포 | **없음** (웹 기반 프로토타입) |

**결론: 현재 산출물은 "완성된 설계"이지 "동작하는 서비스"가 아니다.**
제안서에서 이 구분을 흐리면 심사·시설 실사에서 바로 드러난다. 그래서 우리는 이렇게 말한다.

> "우리는 무엇을 만들지 화면 단위로 다 정했고, 법적 경계까지 그어 두었다.
> 아직 만들지 않은 것은 이를 실제로 굴리는 서버다. 그 범위와 순서를 이 문서에 적었다."

## 1. 단계 설계

```
Phase 0  최소 동작 시스템 개발      [필수 선행 · 미착수]
Phase 1  파트너 확보 + 사전조사      [미착수]
Phase 2  8주 파일럿                  [미착수]
Phase 3  결과 정리 → 시범사업 지원   [미착수]
```

### Phase 0 — 최소 동작 시스템 (선행 조건)

**원칙: 4역할 전부를 만들지 않는다. 한 축만 실제로 굴린다.**

살릴 축 (가장 가치가 크고 법적으로 가장 안전한 경로):

```
요양보호사 입력  →  서버 저장  →  가족 앱 일일 리포트 수신
```

| 만드는 것 | 만들지 않는 것 (파일럿 범위 밖) |
|---|---|
| 계정·로그인, 역할별 권한 | 의료진 웹 대시보드 전체 |
| 요양보호사 체크리스트 입력 | 실시간 채팅 |
| 하루 1회 리포트 생성·발송 | 영상통화 |
| 가족 앱 리포트 열람 | 결제·정산 |
| 동의 이력 저장, 접속기록 2년 | 앱스토어 정식 배포 (웹앱으로 진행) |
| 전송·저장 암호화 | AI 자동 요약 (초기엔 템플릿, 검증 후 도입) |

**AI는 Phase 0에서 뒤로 뺀다.** 이유: (1) 비용·정확도 리스크, (2) SaMD 경계 논란을 파일럿 단계에서 만들 필요가 없음, (3) "AI가 요약해준다"보다 **"매일 도착한다"** 자체가 검증 대상이기 때문. 템플릿 문장으로 먼저 검증하고, 효용이 확인되면 AI를 얹는다.

**현실적 개발 경로 3안**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. BaaS 직접 개발 | Next.js + 관리형 백엔드(인증·DB·스토리지) | 팀 통제, 비용 최소 | 팀에 개발 인력 필요 |
| B. 개발자 합류 / 산학 연계 | 학내 개발 전공·연구실 협업 | 속도 | 일정·지속성 불확실 |
| C. 컨소시엄 개발 위탁 | 시범사업 파트너사가 구현, 우리는 설계·UX 담당 | 규모 대응 | 우리가 주도권을 잃을 수 있음 |

> **권고: A를 기본, C를 병행 탐색.** 시범사업은 어차피 지자체 컨소시엄이 필수이므로, C 경로에서 우리 역할을 "서비스 설계·UX·법 준수 설계 담당"으로 정의해두면 개발 인력 부족이 결격 사유가 되지 않는다.

**Phase 0 완료 기준(Definition of Done)**
1. 요양보호사 계정이 체크리스트를 입력하면 서버에 저장된다
2. 매일 정해진 시각에 가족 계정으로 리포트가 발송된다
3. 가족이 로그인해 과거 리포트를 열람할 수 있다
4. 동의 화면이 실제 동의 이력을 저장한다
5. 전송·저장 암호화, 접속기록 저장이 켜져 있다
6. 역할별로 볼 수 없는 데이터가 실제로 차단된다

### Phase 1 — 파트너 확보 + 사전조사

**섭외 대상 (우선순위)**
1. 지도교수·학교를 통한 소개 (warm intro) — 콜드 컨택 성공률이 낮은 영역이다
2. 지역 입소형 장기요양기관 (전국 6,361개소 중 접근 가능한 소규모 시설)
3. 기초지자체 돌봄·노인복지 부서 — 시범사업 컨소시엄 구성의 필수 파트너

**사전조사 항목 (근거를 못 구해 파일럿으로 넘긴 것들)**

| 항목 | 왜 필요한가 |
|---|---|
| 시설 와이파이 커버리지, 공용 기기 보유 | 도입 현실 리스크. 국내 통계 확보 실패 |
| 요양보호사 1인당 기록·서류 소요 시간 (기준선) | **핵심 KPI의 사전값.** 국내 정량 통계 없음 |
| 가족 문의 전화·방문 빈도 (기준선) | 효용 측정의 사전값 |
| 어르신 스마트기기 사용 가능 인원 비율 | 환자앱 적용 범위 |
| 비용 부담 주체 인식 (시설/가족/공공) | 수익모델 현실성 |
| 기존 기록 시스템(전자·수기) 현황 | 중복 입력 리스크 |

> 이 6개 항목은 **제안서가 "확인 필요"로 남긴 빈칸과 정확히 일치한다.**
> 즉 파일럿은 제품 검증이자 **리서치 공백 해소 수단**이다. 심사에서 이 점을 명시한다.

### Phase 2 — 8주 파일럿

| 항목 | 설계 |
|---|---|
| 규모 | 시설 1곳 · 어르신 10명 내외 · 가족 10명 내외 · 요양보호사 3~5명 |
| 기간 | 8주 (사전 2주 + 운영 6주) |
| 대상 선정 | **치매로 의사결정 능력이 저하된 어르신은 1차 파일럿에서 제외** — 대리동의 입법 공백(민법 제938조·제947조의2)이 해소되지 않았으므로, 본인 동의가 가능한 분부터 시작한다 |
| 동의 | 민감정보 별도 동의 + 제3자 제공 동의를 종이·전자 양쪽으로 받고 이력 보관 |
| 데이터 최소화 | 파일럿에 필요한 항목만 수집. 진료기록에 해당할 수 있는 항목은 **수집하지 않는다**(회색지대 회피) |
| 철회 | 언제든 중단 가능, 중단 시 데이터 삭제 |
| 종료 후 | 수집 데이터 파기 또는 익명화, 파기 확인서 발급 |

**법적 문턱 (확인 완료)**
- 개인정보 영향평가(PIA)는 **공공기관 + 5만명 이상 민감정보**가 법정 의무 기준(법 제33조①·시행령 제35조). **민간 시설 소규모 파일럿은 법정 의무 아님.**
- CSAP는 클라우드컴퓨팅법 제23조의2로 **국가·공공 대상 서비스** 초점. 민간 요양시설에는 강제되지 않음.
- 단 **민감정보 별도 동의·안전성 확보조치·최소수집은 규모와 무관하게 적용**된다.
- **연구윤리** — 결과를 논문·공모 발표에 쓸 경우 학내 IRB(생명윤리위원회) 심의 필요 여부를 사전에 확인한다. 이는 법이 아니라 학교 규정 영역이므로 **지도교수 확인 필요**.

### Phase 3 — 결과 정리 → 시범사업

- 파일럿 결과 보고서 (KPI 사전·사후 비교, 정성 인터뷰 포함)
- 실패·미달 항목도 그대로 기재 — 심사에서 신뢰를 만드는 것은 성공률이 아니라 측정의 정직성이다
- 지자체와 컨소시엄 구성 → 스마트 사회복지시설 시범사업 등 차기 공고 지원

## 2. KPI — 무엇을 어떻게 재는가

| # | 지표 | 측정 방법 | 사전값 | 성공 기준(가설) |
|---|---|---|---|---|
| K1 | 가족의 시설 문의 횟수 | 시설 응대 기록 (주 단위) | Phase 1에서 2주 측정 | 유의미한 감소 관찰 |
| K2 | 요양보호사 기록·응대 소요 시간 | 자기기입 타임로그 (주 2회) | 〃 | 증가하지 않을 것 **(중요: 감소가 아니라 '증가하지 않음'이 1차 목표)** |
| K3 | 가족 안심도 | 동일 문항 사전·사후 설문 | 사전 설문 | 상승 |
| K4 | 리포트 열람률 | 서버 로그 | — | 6주 평균 열람률 유지 |
| K5 | 어르신 앱 사용 지속 | 서버 로그 | — | 이탈 시점·사유 기록 |
| K6 | 이상 상황 전달 소요 시간 | 이벤트 타임스탬프 | 〃 | 단축 |

**K2에 대한 주의** — 새 시스템은 초기에 **입력 부담을 늘린다.** 이를 숨기고 "부담이 줄어든다"고 주장하면 현장에서 바로 반박당한다.
따라서 1차 목표를 "감소"가 아니라 **"기존 기록을 대체하여 총량이 늘지 않는 것"** 으로 잡는다. 이것이 현장에서 통하는 약속이다.

**표본 한계 명시** — 시설 1곳·10명은 통계적 유의성을 주장할 수 없는 규모다.
결과는 **"통계적 증명"이 아니라 "실현 가능성과 현장 수용성의 확인"** 으로 표현한다. 과장하지 않는 것이 다음 단계 신뢰를 만든다.

## 3. 리스크와 대응

| 리스크 | 가능성 | 대응 |
|---|---|---|
| 시설 섭외 실패 | **높음** — 레퍼런스·법인격 없는 학생 팀 | 지도교수·학교 경유. 무상 제공. 시설 부담을 "요양보호사 1일 5분 입력"으로 최소화 |
| 개발 인력 부족 | **높음** | Phase 0 범위를 1개 축으로 축소. 컨소시엄 위탁(C안) 병행 |
| 요양보호사 거부감 | 중 | 기존 기록을 **대체**하도록 설계(추가 아님). 종이 기록 병행 기간 확보 |
| 가족 기대 과열 | 중 | "매일 온다"만 약속. 의료적 판단·응급 대응은 약속하지 않음 |
| 개인정보 사고 | 낮음·영향 큼 | 최소수집, 암호화, 접속기록, 파기 절차. 사고 시 즉시 중단·통지 |
| 어르신 앱 미사용 | 중 | 환자앱은 **선택 기능**으로 두고, **가족-요양보호사 축**만으로도 성립하도록 설계 |
| 규제 판단 지연 | 중 | 파일럿 범위를 비의료(급여제공기록 공유)로 한정해 유권해석 없이도 진행 가능하게 |

## 4. 자원 · 일정 (현실 추정)

> 아래는 팀 3인(디자인 중심, 전임 아님) 기준의 **추정치이며 확정 일정이 아니다.**

| 단계 | 소요(추정) | 주요 전제 |
|---|---|---|
| Phase 0 개발 | 2~4개월 | 개발 인력 확보 여부에 전적으로 좌우 |
| Phase 1 섭외·사전조사 | 1~2개월 | Phase 0과 병행 가능 |
| Phase 2 파일럿 | 2개월 | — |
| Phase 3 정리·지원 | 1개월 | 공고 시점에 종속 |

**비용 항목** — 서버·DB 호스팅, 도메인, (도입 시) AI API, 파일럿 기기 대여, 인쇄·동의서.
공모·지원사업 자금 없이 자부담으로 감당 가능한 규모로 Phase 0을 설계한다.

**일정의 진짜 제약** — 정부 사업 공고는 대체로 연 1회다.
2026년 AX-Sprint는 4월에 마감했고 스마트 사회서비스 시범사업 2차 공고도 진행됐다.
따라서 **현실적 목표는 2027년 회차이며, 그 전까지 파일럿 결과를 만드는 것이 유일하게 의미 있는 준비**다.
