# 하루안부 디자인 시스템 관리 자동화 계획

작성일: 2026-05-23  
대상 앱: `v11_보호자앱`, `v11_요양보호사앱`, `v15_의료진앱`, 필요 시 `v10_의료진웹`  
목적: 보호자앱, 요양보호사앱, 의료진앱이 각자 따로 만든 앱처럼 보이지 않고, 같은 서비스의 역할별 앱처럼 보이도록 디자인 요소를 정리하고 관리한다.

## 1. 현재 상황 요약

하루안부에는 이미 공통 디자인의 재료가 있다.

- `07_디자인/tokens/tokens.css`: 색상, 글자 크기, 여백, 카드 모서리, 그림자 같은 기본 디자인 값
- `07_디자인/system/components.css`: 버튼, 카드, 탭바 등 공통 UI 부품
- `v11_요양보호사앱/caregiver.css`: 요양보호사앱 중심의 모바일 공통 스타일
- `v15_의료진앱/_shared.css`: 의료진 모바일앱 공통 스타일
- `v11_보호자앱/common.css`: 보호자앱 레거시 호환 스타일

다만 현재는 화면마다 인라인 스타일과 로컬 CSS가 많이 남아 있다. 그래서 한 화면을 고치면 그 화면만 좋아지고, 다른 앱과의 일관성은 다시 깨질 수 있다.

즉, 지금 필요한 일은 새 디자인을 처음부터 만드는 것이 아니라, 이미 만든 화면에서 좋은 요소를 골라 공식 부품으로 정하고, 나머지 화면을 그 기준에 맞추는 것이다.

## 2. 디자이너 관점의 목표

코드의 토큰이나 CSS 구조보다 중요한 목표는 다음이다.

- 세 앱이 같은 서비스의 제품군처럼 보여야 한다.
- 보호자앱, 요양보호사앱, 의료진앱의 역할 차이는 유지해야 한다.
- 버튼, 카드, 탭바, 헤더, 상태 배지 같은 반복 요소는 피그마 컴포넌트처럼 같은 스타일을 가져야 한다.
- 화면을 하나씩 수정해도 전체 디자인 시스템이 무너지지 않아야 한다.
- 디자이너가 코드 파일을 보지 않아도 공통 부품을 눈으로 확인할 수 있어야 한다.

## 3. 통일해야 할 공통 부품

우선 아래 요소를 공식 컴포넌트로 정리한다.

- 앱 헤더
- 아이콘 버튼
- 하단 탭바
- SOS 버튼
- 기본 카드
- 위험 카드
- 상태 배지
- 주요 버튼
- 리스트 행
- AI 안내 카드
- 바텀시트
- 입력 필드

이 요소들은 화면마다 새로 만들지 않고, 공통 스타일을 가져다 쓰는 방식으로 정리한다.

## 4. 앱별 차이는 이렇게 유지한다

모든 앱을 똑같이 만들면 안 된다. 같은 부품을 쓰되 역할별 톤은 달라야 한다.

### 보호자앱

- 역할: 안심, 해석, 가족 관점의 이해
- 주요 톤: 블루
- 정보 밀도: 낮음에서 중간
- 문장 톤: 부드럽고 설명적
- 유지할 고유 요소: 안부형 홈, AI 오브, 일일 리포트 시트

### 요양보호사앱

- 역할: 현장 실행, 기록, 호출
- 주요 톤: 그린
- 정보 밀도: 중간
- 조작 방식: 큰 터치 영역, 명확한 CTA
- 유지할 고유 요소: 지금 할 일, 기록 시작, 현장 호출

### 의료진앱

- 역할: 판단, 우선순위, 임상 액션
- 주요 톤: 그린 기반, 필요 시 의료 정보 블루 보조
- 정보 밀도: 높음
- 조작 방식: 위험 환자 확인, 회진, 인수인계 중심
- 유지할 고유 요소: 위험 근거, 미처리 임상 액션, 우선순위 큐

## 5. 수정할 때의 판단 기준

화면 하나를 보다가 수정할 일이 생기면, 바로 그 화면만 고치지 않는다. 먼저 수정 범위를 판단한다.

### 전체 공통으로 고칠 것

- 버튼 높이
- 카드 모서리
- 기본 그림자
- 탭바 형태
- 헤더 높이
- 아이콘 버튼 크기
- 상태 배지 형태
- SOS 색상과 기본 형태

수정 위치: `07_디자인/system/components.css` 또는 `07_디자인/tokens/tokens.css`

### 역할별로 고칠 것

- 보호자앱만 더 부드럽게 보여야 하는 경우
- 요양보호사앱만 버튼이나 글자가 더 커야 하는 경우
- 의료진앱만 정보 밀도가 높아야 하는 경우

수정 위치: 역할별 토큰 또는 앱 공통 CSS

### 화면 개별로 고칠 것

- 보호자 홈 AI 오브 위치
- 특정 화면의 섹션 순서
- 특정 카드 안의 콘텐츠 배치
- 특정 화면만의 인터랙션

수정 위치: 해당 화면의 로컬 스타일

## 6. 앞으로의 작업 원칙

화면을 수정할 때는 다음 순서를 따른다.

1. 문제를 발견한다.
2. 공통 문제인지, 역할별 문제인지, 화면 개별 문제인지 판단한다.
3. 공통 문제라면 디자인 시스템 원본을 먼저 수정한다.
4. 역할별 문제라면 앱 공통 CSS에서 수정한다.
5. 화면 개별 문제라면 해당 화면만 수정한다.
6. 수정 후 컴포넌트 보드와 대표 화면 3개를 확인한다.
7. 변경 기록을 남긴다.

피그마로 비유하면, 인스턴스를 임의로 detach해서 고치는 것이 아니라 메인 컴포넌트를 먼저 수정할지 판단하는 방식이다.

## 7. 필요한 자동화

반복 점검을 줄이기 위해 자동 검사 도구를 만든다.

### 7.1 디자인 감사 스크립트

예상 파일:

```text
07_디자인/scripts/design_audit.py
```

검사 항목:

- 직접 색상값 사용 여부: `#2C7AFC`, `#F4FAF6` 등
- 직접 그림자값 사용 여부
- 직접 `border-radius` 남용 여부
- 공통 CSS import 누락 여부
- 화면 안에서 버튼, 카드, 탭바를 새로 정의했는지 여부
- 이모지 사용 여부
- `iconify-icon`이 아닌 아이콘 사용 여부
- `components.css` 대신 로컬 스타일로 공통 부품을 덮어쓴 경우

결과 예시:

```text
[경고] v11_보호자앱/g02-ai-report.html
- 직접 색상 #fff 사용 3건
- .custom-card에서 border-radius 직접 지정
- 공통 .card 대신 로컬 카드 스타일 사용

[정상] v11_요양보호사앱/c01-today.html
- 공통 토큰 사용
- 헤더/탭바 기준 통과
```

### 7.2 컴포넌트 보드

예상 파일:

```text
07_디자인/role-component-board.html
```

목적:

- 디자이너가 코드 없이 공통 부품을 눈으로 확인한다.
- 보호자, 요양보호사, 의료진의 같은 컴포넌트를 나란히 비교한다.
- 새 화면을 만들 때 기준으로 삼는다.

포함할 항목:

- 헤더 3종 비교
- 버튼 3종 비교
- 기본 카드 3종 비교
- 위험 카드 3종 비교
- 상태 배지 비교
- 하단 탭바 비교
- SOS 버튼 비교
- AI 카드 비교
- 리스트 행 비교
- 바텀시트 비교

### 7.3 대표 화면 자동 확인

대표 화면:

- 보호자 홈: `v11_보호자앱/g-guardian-live.html`
- 요양보호사 오늘: `v11_요양보호사앱/c01-today.html`
- 의료진 지금: `v15_의료진앱/d01-home.html`

자동 확인 항목:

- 화면이 정상 로드되는가
- 콘솔 오류가 없는가
- 헤더, 탭바, 주요 카드가 화면에 보이는가
- 스크린샷을 저장해 비교할 수 있는가

예상 명령:

```bash
python3 07_디자인/scripts/design_audit.py
```

또는 추후:

```bash
python3 07_디자인/scripts/visual_check.py
```

## 8. 우선순위

### 1단계: 기준 만들기

- `07_디자인/role-component-board.html` 제작
- 대표 화면 3개를 기준 화면으로 확정
- 공통 컴포넌트 목록 확정

### 2단계: 자동 검사 만들기

- `design_audit.py` 제작
- 직접 색상값, 이모지, 공통 CSS import 누락 등 우선 검사
- 경고 리포트 방식으로 운영

### 3단계: 대표 화면 정리

- 보호자 홈
- 요양보호사 오늘
- 의료진 지금

이 3개 화면을 컴포넌트 보드 기준으로 맞춘다.

### 4단계: 나머지 화면 확장

- 보호자앱 서브 화면
- 요양보호사앱 서브 화면
- 의료진앱 서브 화면
- 필요 시 의료진 웹

### 5단계: 작업 규칙 고정

`AGENTS.md` 또는 별도 작업 가이드에 다음 규칙을 추가한다.

- 화면 수정 전 디자인 감사 실행
- 공통 컴포넌트 영향 여부 판단
- 공통 문제면 `components.css` 또는 `tokens.css` 수정
- 화면 개별 문제면 해당 화면만 수정
- 수정 후 대표 화면 3개 확인

## 9. 앞으로 Codex/Claude에게 요청할 때의 문장 예시

화면을 수정할 때는 아래처럼 요청한다.

```text
이 화면을 수정하되, 공통 컴포넌트 영향 여부도 같이 판단해줘.
공통 요소 문제면 디자인 시스템 쪽을 먼저 고치고,
이 화면만의 문제면 로컬 스타일로 처리해줘.
수정 후 보호자/요양보호사/의료진 대표 화면도 확인해줘.
```

컴포넌트 보드를 만들 때는 아래처럼 요청한다.

```text
현재 하루안부 앱들의 기존 디자인을 기반으로
피그마 컴포넌트 보드처럼 볼 수 있는 HTML 컴포넌트 보드를 만들어줘.
보호자, 요양보호사, 의료진의 같은 부품을 나란히 비교할 수 있게 해줘.
```

자동 검사 도구를 만들 때는 아래처럼 요청한다.

```text
화면별 디자인 일관성 감사 스크립트를 만들어줘.
직접 색상값, 직접 그림자값, 이모지, 공통 CSS import 누락,
로컬 버튼/카드/탭바 재정의를 검사해서 리포트로 보여줘.
```

## 10. 결론

지금 하루안부에 필요한 것은 새 디자인을 다시 만드는 것이 아니라, 이미 존재하는 디자인을 정리해서 운영 가능한 시스템으로 만드는 것이다.

핵심은 다음 세 가지다.

1. 디자이너가 볼 수 있는 컴포넌트 보드
2. 코드가 규칙을 어기는지 잡아내는 감사 스크립트
3. 화면 수정 시 공통/역할별/개별 수정 범위를 먼저 판단하는 작업 흐름

이 구조를 만들면 앞으로 화면 하나를 수정해도 디자인 시스템이 무너지지 않고, 보호자앱, 요양보호사앱, 의료진앱이 같은 서비스의 제품군처럼 유지될 수 있다.
