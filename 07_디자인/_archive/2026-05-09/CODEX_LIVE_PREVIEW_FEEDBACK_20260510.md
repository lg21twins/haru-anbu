검토일: 2026-05-10  
검토 URL: `http://localhost:8765/07_디자인/preview.html`  
검토 범위: `preview.html`, `preview-components.html`, `preview-patterns.html`, `preview-roles.html` 실제 렌더링 기준  
목적: 클로드가 만든 디자인 시스템 프리뷰를 더 세련되고, 실제 앱 적용 가능한 기준 문서로 만들기 위한 생산적 비판

## 0. 파일 직접 검토 추가 메모

요청에 따라 캡쳐 기준이 아니라 `preview.html` 파일 전체 460줄과 `_preview-shared.css`, `preview-components.html`, `preview-roles.html`, `tokens.css`의 연결 구조를 직접 확인했다.

파일 기준으로 보면 가장 큰 문제는 더 명확하다.

- `preview.html`은 제목과 버전은 v3.1로 정리됐지만, 핵심 원칙 2번은 여전히 "글래스모피즘이 기본"이라고 말한다.
- 반면 `tokens.css`와 `preview-components.html`은 "flat first, glass selective"를 말한다.
- 즉, 디자인 시스템의 진입점인 `preview.html`이 아직 최신 철학을 완전히 반영하지 못했다.

이건 단순 문구 문제가 아니라 팀 기준을 흔드는 문제다. 누군가는 `preview.html`의 핵심 원칙을 보고 일반 카드에 glass를 계속 쓸 수 있고, 누군가는 `02_COMPONENTS.md`를 보고 flat card로 만들 수 있다. 그러면 지금 앱들이 이미 겪고 있는 "화면마다 다른 스타일" 문제가 반복된다.

가장 먼저 고칠 부분:

```html
<!-- preview.html 현재 핵심 원칙 2번 -->
<strong>글래스모피즘이 기본</strong> — 카드는 반투명 흰색 + blur(16px) + 프로스티드 하이라이트. 단단한 흰 카드는 예외다.
```

권장 수정:

```html
<strong>Flat surface가 기본</strong> — 일반 정보 카드는 흰 surface + 1px border + 약한 shadow. Glass는 탭바·모달·AI 리포트·환자 가족 사진 카드처럼 플로팅/감성 맥락에만 제한적으로 쓴다.
```

이 한 줄을 고치지 않으면 v3.1의 핵심 방향이 흐려진다.

## 1. 한 줄 결론

현재 프리뷰는 이전보다 훨씬 정돈됐다. `v3.1`로 방향도 맞고, `Flat first / Glass selective` 철학도 보인다. 다만 아직 "보기 좋은 문서"에 가깝고, "앱 전체를 이끌 강한 디자인 시스템"으로 보이려면 몇 가지 보완이 필요하다.

가장 큰 보완점은 세 가지다.

1. 첫 화면이 너무 조용해서 실제 제품 UI의 매력을 바로 증명하지 못한다.
2. Components/Patterns 일부 예시는 아직 토큰 정책보다 데모용 스타일에 가깝다.
3. 모바일에서 Roles 표가 깨져 문서 자체의 완성도가 낮아 보인다.

---

## 2. 잘 된 점

### 2.1 전체 톤은 깔끔해졌다

첫 화면은 과한 장식이 없고, 흰색과 연한 캔버스 배경 중심이라 훨씬 정돈돼 보인다. 이전 앱 화면들에서 보였던 과한 blur, radial gradient, glass 남발에 비해 이번 프리뷰는 훨씬 전문적이다.

특히 좋은 점:

- 네비게이션이 단순하다.
- 로고, 버전, 섹션 카드가 안정적으로 배치되어 있다.
- 카드 간격과 표면 톤이 차분하다.
- `v3.1`이라는 기준이 명확히 보인다.

### 2.2 Components 페이지는 실제로 쓸 수 있는 카탈로그에 가까워졌다

버튼, FAB, chip, card, sheet, modal, tabbar, input, badge, toast, SOS, timeline 등 필요한 범위가 잘 잡혀 있다.

좋은 방향:

- 컴포넌트 카테고리가 명확하다.
- `card 4종` 철학이 살아 있다.
- glass를 "예외 사용"으로 분리한 점이 좋다.
- Input 상태 예시는 실제 구현 기준으로 쓸 수 있다.

### 2.3 Patterns 페이지는 실제 앱 적용을 상상하게 만든다

`보호자 홈 — 오늘 안심 확인` 같은 패턴 명명은 좋다. 컴포넌트만 나열하는 것보다 실제 화면 조합을 보여주기 때문에 팀원이 "이걸 앱에 어떻게 쓰지?"를 이해하기 쉽다.

### 2.4 Roles 페이지의 메시지는 좋다

"큰 카드 색을 칠하지 않는다. accent는 보조 신호일 뿐"이라는 메시지는 매우 좋다. 기존 앱들이 역할별로 너무 다른 감각을 갖는 문제를 줄일 수 있다.

## 3. 핵심 문제와 개선안

## 3.1 첫 화면이 너무 얌전해서 설득력이 약하다

현재 `preview.html` 첫 화면은 깔끔하지만, 디자인 시스템의 힘을 즉시 보여주지는 못한다. 문서 인덱스처럼 보인다.

문제:

- 첫 화면에서 실제 앱 UI를 거의 볼 수 없다.
- "하나의 차체, 세 개의 테마"라는 문장은 좋은데, 시각적으로 바로 증명되지 않는다.
- 카드 4개는 문서 링크로 보이고, 제품 UI 프리뷰로 느껴지지 않는다.

개선안:

첫 화면 hero 아래에 바로 "3역할 미니 앱 프리뷰"를 넣는 것이 좋다.

권장 구조:

```text
Hero
↓
Guardian / Caregiver-Medical / Patient 3개 미니 화면 비교
↓
Foundations / Components / Patterns / Roles 카드
↓
Docs
↓
Principles
```

이렇게 하면 방문자가 바로 이해한다.

> "아, 이 DS를 적용하면 보호자/의료진/환자 앱이 같은 제품군처럼 보이겠구나."

지금은 이 메시지를 읽어야 이해한다. 디자인 시스템 프리뷰라면 읽기 전에 보여줘야 한다.

---

## 3.2 문서 카드가 정보는 좋은데 시각적 위계가 약하다

첫 화면의 Foundations, Components, Patterns, Roles 카드가 모두 같은 무게로 보인다. 실제로는 적용 순서가 있다.

권장 위계:

1. `tokens.css` / Foundations: 진실의 원천
2. Components: 실제 앱 코드 기준
3. Patterns: 화면 조합
4. Roles: 역할별 검증

개선안:

- 첫 카드인 Foundations 또는 `tokens.css`를 더 명확히 "Source of Truth"로 표시
- Components 카드에는 "앱 적용 시 우선 사용" 같은 배지 추가
- Patterns 카드는 "실제 화면 레시피"로 명명
- Roles 카드는 "QA 기준" 또는 "역할별 검증"으로 포지셔닝

현재 카드 제목은 좋지만, 각 카드가 어떤 의사결정을 책임지는지 조금 약하다.

---

## 3.3 Components 페이지의 버튼 예시는 깔끔하지만 브랜드 감각이 약간 평범하다

버튼 스펙은 좋다. 다만 시각적으로는 일반 SaaS 문서와 크게 다르지 않다. 하루안부만의 특징이 덜 보인다.

개선안:

- Primary 버튼은 좋지만, "의료/돌봄 앱에서 쓰는 실제 라벨"로 예시를 바꾸면 좋다.

현재 느낌:

```text
확인 / 취소 / 삭제하기 / 자세히 보기 / 메시지 보내기
```

권장 예시:

```text
기록 저장
복용 완료
보호자에게 공유
간호사 호출
AI 요약 보기
```

디자인 시스템은 추상 컴포넌트보다 "제품 언어"를 같이 보여줄 때 설득력이 커진다.

---

## 3.4 Patterns 페이지의 디바이스 프리뷰가 좋지만, 화면이 너무 아래에서 시작한다

데스크톱에서 `preview-patterns.html`을 보면 상단 설명 이후 디바이스가 중앙에 크게 들어와서 좋다. 하지만 첫 viewport에서는 디바이스 상단만 보이고, 실제 패턴의 핵심이 아래로 밀린다.

문제:

- 프리뷰 페이지에서 가장 중요한 앱 화면이 한눈에 완전히 들어오지 않는다.
- 기기 프레임이 너무 크고, 문서 헤더와 설명이 위 공간을 많이 차지한다.

개선안:

- 패턴 페이지의 device height를 조금 줄이거나 scale을 적용
- `P1. 보호자 홈` 제목과 디바이스를 2열로 배치
- 데스크톱에서는 설명 왼쪽, 디바이스 오른쪽 배치

권장 구조:

```text
[패턴 설명 / 핵심 규칙 / Do-Don't]  [미니 디바이스 프리뷰]
```

이렇게 하면 실제 화면 패턴을 더 빠르게 검토할 수 있다.

## 3.5 Roles 페이지는 모바일에서 깨진다

가장 시급한 렌더링 문제다. 390px 폭에서 Roles의 역할 표가 카드 안에서 3열 구조를 유지하다가 오른쪽 설명 텍스트가 지나치게 좁아져 세로로 잘린다.

증상:

- `가족의 하루 상태를...` 설명이 오른쪽 좁은 칸에서 세로 줄바꿈된다.
- 보호자 카드가 비정상적으로 커 보인다.
- 모바일에서 문서 신뢰도가 떨어진다.

개선안:

모바일에서는 역할 행을 무조건 세로 스택으로 바꿔야 한다.

권장 CSS:

```css
@media (max-width: 640px) {
  .role-row {
    display: grid;
    grid-template-columns: 1fr;
    gap: var(--space-3);
  }

  .role-row__dot {
    align-self: start;
  }

  .role-row__meta {
    display: flex;
    align-items: center;
    gap: var(--space-3);
  }

  .role-row__desc {
    grid-column: 1;
    font-size: var(--text-callout);
    line-height: var(--leading-relaxed);
  }
}
```

또는 더 단순하게:

```text
[dot 보호자]
data-role="guardian" · #2C7AFC
가족의 하루 상태를 매일 안심하게 확인...
```

모바일 문서에서는 표보다 카드형 설명이 훨씬 읽기 쉽다.

## 3.6 네비게이션 모바일 대응이 어색하다

390px에서 상단 네비가 두 줄/세로 흐름처럼 보인다. 기능적으로는 깨지지 않았지만, 디자인 시스템 문서의 첫인상으로는 다소 어색하다.

개선안:

모바일에서는 네비 링크를 가로 스크롤 pill row로 바꾸는 것이 좋다.

권장:

```css
@media (max-width: 640px) {
  .pv-nav__inner {
    display: grid;
    grid-template-columns: 1fr auto;
    gap: var(--space-3);
  }

  .pv-nav__links {
    grid-column: 1 / -1;
    overflow-x: auto;
    flex-wrap: nowrap;
    margin-left: 0;
    padding-bottom: var(--space-2);
  }

  .pv-nav__link {
    white-space: nowrap;
  }
}
```

## 3.7 Favicon 404는 작지만 바로 고치는 게 좋다

콘솔에서 `favicon.ico` 404가 난다. 기능 문제는 아니지만 디자인 시스템 문서는 polish가 중요하다.

개선안:

`preview*.html` 공통 head에 favicon을 명시한다.

```html
<link rel="icon" type="image/svg+xml" href="logo/brand-system/01_심볼단독.svg">
```

## 3.8 "의료진 + 요양보호사"를 하나로 묶은 설명은 조금 위험하다

역할 비교에서는 의료진과 요양보호사를 한 줄로 묶고 있다. 제품군 관점에서는 이해되지만, UX 관점에서는 두 사용자는 꽤 다르다.

문제:

- 의료진: 판단, 위험, 회진, 인수인계, EMR성 정보
- 요양보호사: 체크리스트, 현장 기록, 한 손 조작, 다국어 가능성

개선안:

Roles 페이지에서 색상은 같은 green 계열로 묶되, UX density는 따로 보여줘야 한다.

권장 역할 분리:

```text
보호자: 안심 확인
의료진: 위험 판단 + 업무 큐
요양보호사: 현장 기록 + 체크리스트
환자: 지금 할 일 + 가족 연결
```

색상 테마는 3개여도, 사용 시나리오 카드는 4개가 맞다.

## 4. 더 깔끔한 디자인으로 가는 구체 수정안

### 4.1 Preview Home

수정:

- hero 아래에 3개 또는 4개 역할 미니 앱 프리뷰 추가
- 문서 카드보다 실제 UI를 먼저 보여주기
- "하나의 차체"를 말로 설명하지 말고, 같은 컴포넌트 구조가 역할별로 변하는 모습을 보여주기

권장 문구:

```text
같은 구조, 다른 맥락
보호자는 안심을 확인하고, 의료진은 위험을 판단하고, 요양보호사는 현장을 기록하고, 환자는 지금 할 일을 쉽게 실행합니다.
```

### 4.2 Components

수정:

- 버튼 라벨을 실제 하루안부 문맥으로 교체
- `card-default`, `card-action`, `card-alert`, `card-hero`를 한 화면에서 명확히 비교
- "Glass optional"은 더 아래로 내리거나 별도 warning callout 추가

좋은 표시:

```text
Glass는 예쁜 카드가 아니라 레이어다.
정보 카드에는 쓰지 않는다.
```

### 4.3 Patterns

수정:

- 데스크톱에서는 설명 + 디바이스 2열
- 모바일에서는 디바이스 scale down
- 각 패턴 아래에 "이 패턴이 실제 앱에서 대응하는 파일" 추가

예:

```text
Applies to:
- v11_보호자앱/g-guardian-live.html
- v11_보호자앱/g02-ai-report.html
```

### 4.4 Roles

수정:

- 모바일 표 깨짐 수정
- 의료진과 요양보호사 UX density 분리
- 역할별 "주요 화면 목표"를 더 명확히 표시

권장:

```text
보호자: 오늘 상태를 10초 안에 안심하고 확인
의료진: 위험 환자와 다음 업무를 즉시 판단
요양보호사: 현장에서 빠르게 기록하고 누락 방지
환자: 지금 할 일을 큰 버튼으로 실행
```

## 5. 우선순위

### P0. 바로 고칠 것

- 모바일 Roles 표 깨짐 수정
- favicon 404 수정
- 모바일 nav를 가로 스크롤 pill row로 개선
- Preview Home에 실제 역할별 미니 UI 프리뷰 추가

### P1. 실제 앱 적용 전

- Components 버튼/카드 예시를 하루안부 실제 문맥으로 교체
- Patterns 디바이스 프리뷰를 더 잘 보이게 재배치
- 의료진/요양보호사 UX density 차이를 Roles에 반영

### P2. 앱 적용 단계

- 보호자앱 탭바/카드/FAB부터 적용
- 요양보호사앱은 `card-alert`, `card-action`, 큰 touch target 위주로 적용
- 환자앱은 정보량 축소와 56px 터치 기준 우선
- 의료진앱/웹은 flat + dense + 위험 위계 중심으로 적용

## 6. 최종 평가

클로드가 만든 이번 디자인 시스템은 방향이 좋다. 이전보다 훨씬 깔끔하고, "이제 진짜 디자인 시스템으로 묶어보자"는 의도가 보인다.

하지만 아직은 프리뷰 문서가 실제 앱을 설득하는 힘이 약하다. 첫 화면은 예쁘지만 너무 조용하고, Roles는 모바일에서 깨지고, Components는 일부 예시가 일반 UI 라이브러리처럼 느껴진다.

개선 방향은 명확하다.

> 문서 인덱스처럼 보이는 DS에서, 실제 하루안부 앱을 통일시키는 제품 디자인 시스템으로 바꿔야 한다.

이를 위해서는 첫 화면에 역할별 실제 UI를 보여주고, 모바일 문서 품질을 고치고, 컴포넌트 예시를 하루안부 실제 문맥으로 바꾸는 것이 가장 효과적이다.
